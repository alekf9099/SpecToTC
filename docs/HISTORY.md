# 작업 이력 — 무엇을, 왜 바꿨나

> 커밋 로그는 "무엇"을 남기지만 "왜 그 방향을 골랐는지"는 잘 남지 않는다.
> 여기에는 사용자의 요청과 그때 내린 결정을 PR 단위로 적는다. 새 작업을 시작하기 전에
> 비슷한 일을 이미 시도했다가 되돌린 적이 있는지 여기서 먼저 확인한다.
> 깨면 안 되는 규칙의 요약은 루트의 `CLAUDE.md` 에 있다.

## 흐름 한눈에

1. **#1–#9 기반** — 업로드·TC 구조·요약·로그인(선택)·검증 분석서·PDF 내보내기·테마
2. **#10–#16 웹사이트 분석** — URL → TC, 폼 조건 지정, 브라우저 실행 검증
3. **#17–#24 기획서 품질과 업로드** — PDF 줄 잇기, 요청 확인 항목, CSV 정리, 로그인 탐색, 큰 PDF
4. **#25–#27 QA 가 쓰기 쉬운 TC** — 문구 다듬기, 체크리스트, FRONT 체크 패턴 7가지

## 되돌렸거나 방향을 바꾼 것 — 같은 실수를 반복하지 않기 위해

- **수행 단계의 `QA 는` 주어** — #21 에서 넣었다가 #25 에서 뺐다. 주어를 넣자는 요청의 본뜻은 "무엇을 대상으로 하는지 분명히" 였지
  글자 그대로의 주어가 아니었다. 대상(화면·버튼·값)을 분명히 적는 것으로 해결한다.
- **케이스 종류 이름** — `Pass/Fail` → `정상/실패`(#21) → `기능 확인/오류 처리/경계값`(#26). 번역만으로는 오해가 안 풀렸다.
- **폼 편집기** — 크게 만들었다가(#11·#14) 사용자가 "너무 쓰기 어렵다" 해서 2칸으로 줄였다(#15). 기능을 늘리기보다 입력칸을 줄이는 쪽이 맞았다.
- **업로드 한도** — 서버 한도를 올리는 것으로는 안 됐다(#23). 플랫폼 한도는 우회로(브라우저 추출, #24)로 푼다.

# SpecToTC — 기획서(SRS) 기반 테스트케이스 자동 생성기

> 기획서를 넣으면 Pass / Fail / Edge Case 테스트케이스와 문서 핵심 요약을 만들어 주는 QA 사내 도구.
> 저장소 [alekf9099/SpecToTC](https://github.com/alekf9099/SpecToTC) · 담당 qa@muhayu.com · 최초 작성 2026-08-21

---

## 1. 한 줄 요약

기획서 텍스트·파일(`.md` `.txt` `.pdf` `.docx`)을 넣으면 **테스트케이스 초안**과 **기획 검토용 요약**이 나옵니다. TC 작성에 쓰던 시간을 검토·보완에 쓰는 것이 목표입니다.

## 2. 무엇을 해결하나

| 기존 작업 | SpecToTC 도입 후 |
| --- | --- |
| 기획서를 읽으며 TC를 처음부터 손으로 작성 | 규칙 엔진이 초안 생성 → QA가 검토·보완 |
| 경계값(`8자 이상`, `최대 2회 재시도`)을 눈으로 찾아 케이스화 | 수치 기준을 자동 추출해 경계 ±1 케이스로 전개 |
| 기획서의 모호한 표현을 나중에 발견 | 생성 시점에 "확인 필요" 목록 + 질문 문장으로 제시 |
| 기획 변경 시 어느 TC를 다시 돌릴지 수동 판단 | Diff로 변경 요구사항만 추출 → 회귀 TC 자동 생성 |
| TC를 Excel로 옮길 때 한글 깨짐 | UTF-8 BOM CSV로 내보내기 |

## 3. 처리 흐름

```
.md / .txt / .pdf / .docx
        │
        ▼
   텍스트 추출  (형식 판별 · 인코딩 처리 · PDF 머리글/바닥글 제거)
        │
        ▼
   파서  (요구사항 문장 · 조건절 · 경계값 · 재시도 횟수 추출)
        │
        ├──▶ 규칙 엔진 ──▶ 테스트케이스 (Pass / Fail / Edge)  ──▶ 대시보드 · JSON · CSV
        ├──▶ 요약 엔진 ──▶ 핵심 요구사항 · 수치 기준 · 확인 필요 항목
        └──▶ (선택) Claude 보강 ──▶ 규칙이 놓친 케이스 · 서술형 요약
```

## 4. 기능 정리

### 4.1 입력 — 붙여넣기 또는 파일 업로드

| 형식 | 처리 방식 |
| --- | --- |
| `.md` `.txt` | UTF-8 / UTF-16 BOM 감지, 깨지면 CP949(EUC-KR)로 재디코딩 |
| `.pdf` | `pdfjs-dist` 사용. Node 용 DOMMatrix·ImageData·Path2D 폴리필을 내장해 네이티브 canvas 가 없는 환경(Vercel·다른 OS·optional 의존성 미설치)에서도 동작. 한글 PDF는 CID/Type0 서브셋 폰트를 쓰므로 ToUnicode CMap 해석이 필요해 직접 파싱하지 않음. 페이지마다 반복되는 머리글·바닥글, 페이지 번호·인쇄 시각 줄은 자동 제거 |
| `.docx` | 내장 ZIP 리더로 `word/document.xml` 파싱. Word 제목 스타일 → `#`, 목록 문단 → `- `, 표 → `\| 셀 \| 셀 \|` 로 변환해 **문서 구조를 살린 채** 파서에 전달 |
| `.doc` `.hwp` `.hwpx` | 미지원. `.docx` 또는 PDF로 다시 저장하라는 안내 메시지 반환 |

- 대시보드에서 **드래그 앤 드롭** 또는 클릭해 파일 선택 → 추출 완료 시 TC 생성까지 자동 진행
- 확장자가 없거나 잘못돼도 매직 넘버(`%PDF-`, ZIP 시그니처)로 판별
- 업로드 상한 25MB, 기획서 텍스트 상한 30만자 (환경 변수로 조정)

### 4.2 규칙 엔진 — 감지하는 조건문

| 유형 | 한글 | 영문 |
| --- | --- | --- |
| 조건 분기 | `~일 때` `~하면` `~인 경우` `성공 시` | `if` `when` `once` `in case of` |
| 경계값 | `8자 이상` `20자 이하` `50,000원 이상` `최대 12자` `3초 이내` `8~20자` | `at least 8` `up to 5` `no more than 10` `within 3 seconds` `>= 10` |
| 재시도 | `재시도` `재전송` `최대 2회 재시도` | `retry up to 3 times` `backoff` |
| 이탈 처리 | `이탈` `중단` `타임아웃` `세션 만료` | `abort` `cancel` `timeout` `drop-off` |

전체 **17개 카테고리** (괄호 안은 중요도 가중치):

결제/정산(6) · 개인정보/보안(6) · 삭제·되돌릴 수 없는 동작(6) · 재시도(4) · 이탈·중단(4) · 인증/권한(4) · 입력 검증(4) · 오류/예외(4) · 경계값/임계치(3) · 성능/응답시간(3) · 파일/업로드(3) · 알림/발송(3) · 상태 저장/동기화(3) · 조건 분기(2) · 화면 이동(2) · 목록/검색/정렬(2) · 노출/표시(1)

> 사전은 `src/engine/dictionary.js` 한 파일에 모여 있습니다. 사내 용어(예: `쿠폰 소진`, `정산 마감`)를 여기에 추가하면 바로 반영됩니다.

### 4.3 TC 생성 규칙

| 유형 | 생성 내용 |
| --- | --- |
| **Pass** | 조건 충족 시 명세된 동작이 정상 수행되는 흐름. 상태 저장·알림 카테고리가 있으면 재진입·발송 확인 TC 추가 |
| **Fail** | 조건 미충족 케이스 + 카테고리별 실패 레시피(필수값 미입력, 미인증·권한 없음, 결제 승인 실패, 확장자·용량 초과, 중도 이탈·타임아웃, 서버 5xx 등). 감지된 카테고리가 없으면 네트워크 단절 케이스로 대체 |
| **Edge Case** | 경계값마다 **경계 외부 / 경계 정확값 / 경계 내부** 3점을 한 TC로 묶어 검증. 재시도 상한(N회 소진·초과), 저속 네트워크, 목록 0건·1건·페이지 경계·대량, 이탈 후 재진입, 멱등성(연속 클릭) |

**중요도 산정** — 카테고리 가중치 합 + 유형 보정(Fail +2, Edge +1, 경계값 보유 +1) → `10점 이상 High`, `5점 이상 Med`, 나머지 `Low`.

> 로그인·결제 중심 문서는 High 비중이 커집니다. 팀 기준에 맞게 `generator.js` 의 `calcPriority()` 임계값을 조정하세요.

### 4.4 테스트케이스 구조

**"다른 담당자가 표만 보고 그대로 실행할 수 있는가"** 를 기준으로 설계했습니다.

| 필드 | 내용 |
| --- | --- |
| `tc_id` | `TC-P-001` / `TC-F-001` / `TC-E-001` (AI 보강분은 `TC-E-A001`) |
| `type` · `priority` · `area` | Pass·Fail·Edge Case / High·Med·Low / 요구사항 영역 |
| `title` | `[경계] 1. 로그인 — 경계값 8글자 이상 전후 판정` (유형·영역·검증 대상을 한 줄에) |
| `objective` | **이 TC가 왜 필요한지** 한 문장. 리뷰어가 판단 기준을 잡는 근거 |
| `precondition` | 배열 — 준비물·선행 조건 |
| `steps` | 배열 — `진입:` `준비:` `조건 설정:` `입력:` `실행:` `확인:` 레이블이 붙은 실행 단계 |
| `expected` | 배열 — 검증 포인트를 하나씩 분리 (한 문장에 뭉치지 않음) |
| `requirement` | `{ id, text, line, categories }` — 기획서 원문·라인으로 역추적 |
| `tags` | `boundary` `retry` `spec-gap` `idempotency` 등 |

실제 생성 예시:

```
title        [경계] 1. 로그인 — 경계값 8글자 이상 전후 판정
objective    기준값 8글자 이상 의 경계에서 허용/거부 판정이 정확한지 확인한다.
precondition • 1. 로그인 진입 가능한 테스트 계정/데이터 준비
             • 기준: 8글자 이상 (기획서 표현 "8자 이상")
steps        1. 입력: 7글자 — 경계 외부
             2. 입력: 8글자 — 경계 정확값
             3. 입력: 9글자 — 경계 내부
expected     • 7글자 → 거부 + 유효성 안내
             • 8글자 → 허용 + 정상 처리
             • 9글자 → 허용 + 정상 처리
requirement  REQ-002 (L8) 비밀번호는 8자 이상 20자 이하로 입력해야 한다
```

> 단계에 `실행:` 같은 레이블을 쓴 이유는 한국어 조사 문제로 문장이 어색해지는 것을 피하면서, 표에서 눈으로 스캔하기 쉽게 하기 위함입니다.

### 4.5 문서 요약 — 기획 검토용

우측 패널의 **문서 요약** 탭.

| 항목 | 내용 |
| --- | --- |
| **개요** | 영역·요구사항·조건 분기·수치 기준 수, 언어, 상위 카테고리, TC 커버리지 |
| **핵심 요구사항** | 가중치 점수 상위 N건 (기본 8건). 영역·조건·수치 기준 배지 표시 |
| **수치 기준** | 경계값·재시도 기준을 표로 모아 제공 — 검증 시 그대로 입력값으로 사용 |
| **확인 필요** | 기획에 물어봐야 할 것을 **질문 문장까지** 생성 |
| **영역별 요점** | 영역마다 요구사항 수·주요 카테고리·대표 문장 3건 |

**확인 필요 항목이 잡아내는 것**

- 모호 표현 — `적절히` `필요시` `등` `빠르게` `TBD` `최적화`
- 재시도를 언급했으나 횟수·간격이 없음
- 수치에 단위가 없음
- 조건 분기만 있고 해당 영역에 실패·예외 처리 명세가 없음
- 결제 요구사항에 실패 흐름이 함께 기술되지 않음

같은 사유는 하나로 묶고 해당 요구사항 목록(ID·라인)을 함께 보여줍니다. 예시:

```
[기준 누락] ×1  재시도 언급은 있으나 횟수·간격이 명시되지 않음
  Q: 재시도 최대 횟수와 간격(백오프)을 알려주세요.
  REQ-009 (L18)

[예외 흐름 확인] ×4  결제 관련 요구사항에 실패 시나리오가 함께 기술되지 않음
  Q: 결제 실패·중복 결제·부분 환불 시 처리 정책을 알려주세요.
  REQ-012 (L25), REQ-013 (L26), REQ-015 (L28), REQ-016 (L29)
```

**요약 마크다운 복사** 버튼으로 회의록·티켓에 바로 붙여넣을 수 있습니다.

### 4.6 기획서 비교(Diff)

이전·신규 기획서를 넣으면 Dice 계수 유사도로 문장을 매칭해 **추가 / 수정 / 삭제 / 동일**로 분류합니다.

- 수정 건은 무엇이 바뀌었는지 문장으로 알려줍니다 — 경계값, 재시도 횟수, 조건절, 분류, 영역 이동
- **변경·추가된 요구사항에 대해서만** 회귀 TC(`regression` 태그)를 생성 → 기획 변경 시 회귀 범위 즉시 파악

### 4.7 내보내기

| 버튼 | 형식 | 용도 |
| --- | --- | --- |
| CSV (Excel용·권장) | UTF-8 BOM + CRLF | Excel · 구글 시트. **한글 깨짐 없음** |
| CSV (BOM 없음·연동용) | LF, BOM 없음 | TestRail · Jira 등 BOM을 거부하는 시스템 import |
| JSON | JSON | 자동화 스크립트 연동 |

CSV 컬럼 15개: `TC_ID, 유형, 중요도, 요구사항 영역, 테스트 시나리오, 검증 목적, 사전 조건, 수행 단계, 기대 결과, 요구사항 ID, 근거 문장, 원문 라인, 분류, 태그, 생성 방식`

- 사전 조건·기대 결과는 셀 안에서 `•` 불릿, 수행 단계는 `1. 2. 3.` 번호로 줄바꿈
- 셀이 `=` `+` `-` `@` 로 시작하면 앞에 `'`를 붙여 스프레드시트 수식 인젝션 차단
- 필터가 적용된 **현재 목록만** 내려갑니다
- 양식 변경은 `src/csv.js` 의 `COLUMNS` 배열만 수정

> ⚠️ Excel로 열 때는 반드시 **CSV (Excel용·권장)** 을 사용하세요. 연동용 파일은 BOM이 없어 Excel이 CP949로 잘못 해석해 한글이 깨집니다.

### 4.8 접근 제어 — 기본은 인증 없음

사내에서 쓰는 도구라 **기본값은 로그인 없이 열림**입니다. 로그인 기능은 코드에 들어 있고, 환경 변수 하나(`SPECTOTC_PASSWORD`)로 켤 수 있습니다.

| 설정 | 동작 |
| --- | --- |
| `SPECTOTC_PASSWORD` 비움 **(기본)** | 인증 없이 열림 |
| `SPECTOTC_PASSWORD` 설정 | 로그인 화면 활성화. 팀 공용 비밀번호 → HMAC 서명 HttpOnly 세션 쿠키(기본 12시간). 미인증은 화면 302 / API 401 |
| `SPECTOTC_REQUIRE_AUTH=true` + 비밀번호 없음 | 설정 오류로 보고 503 |

**로그인 없이 운영할 때의 보호 장치**

인증이 없으면 URL을 아는 사람은 누구나 사용할 수 있습니다. 그래서 아래가 함께 들어가 있습니다.

| 항목 | 내용 |
| --- | --- |
| 레이트리밋 | 생성·요약·CSV 60회/분, 업로드 20회/분, AI 보강 12회/시간, 로그인 10회/15분 |
| **AI 키 주의** | `ANTHROPIC_API_KEY` 등록 시 아무나 AI 호출로 크레딧을 소진시킬 수 있음 → `SPECTOTC_AI_TOKEN` 설정 또는 `SPECTOTC_AI_ENABLED=false` 권장 |
| 검색 엔진 차단 | `X-Robots-Tag: noindex, nofollow, noarchive` + robots.txt + 페이지 meta |
| 보안 헤더 | nosniff · no-referrer · X-Frame-Options DENY |
| 로그 위생 | 기획서 본문 대신 메타데이터(형식·바이트·문자 수·처리 시간)만 기록. JSON 파싱 오류에 섞이는 본문 조각도 제거 |

> ⚠️ 레이트리밋은 인메모리 방식이라 Vercel 인스턴스별로만 유지됩니다. 동시 인스턴스가 N개면 실효 한도도 N배입니다. 엄격한 제한이 필요하면 Upstash Redis 등 외부 저장소로 교체해야 합니다.

### 4.9 QA 검증 분석서 (사내 표준 6개 고정 섹션)

요약 아래에 검증 담당자가 그대로 쓸 수 있는 분석서가 함께 생성됩니다. 섹션 순서·제목은 항상 고정입니다.

| 섹션 | 내용 |
| --- | --- |
| **1. QC·QA 검증 진행 시 참고해야 할 점** | 6개 관점(권한·역할 경계 / 입력 검증 / 경계조건 / 예외·에러 처리 / 데이터 정합성 / 검증 환경)별 **"확인할 것 · 왜 · 어떻게"** 표 + **검증 착수 전 준비 체크리스트** |
| **2. 검증 시 진행해야 할 URL** | 화면/기능 · 경로 · 접근 권한 · 핵심 검증 시나리오 표 |
| **3. 프로젝트 동작 흐름** | mermaid flowchart (Notion 에 붙이면 다이어그램으로 렌더) |
| **4. Figma 링크** | 문서의 figma.com 링크. 없으면 `Figma 링크 없음` |
| **5. 목표가 아닌 것 (Out of Scope)** | 추후·차기·미지원 항목 + 문서에 요구사항이 없어 검증 대상이 아닌 영역 |
| **6. 목표 (In Scope)** | 문서의 목적문(없으면 핵심 요구사항 기반 추론) + 검증 통과 시 보장되는 것 |

- 항목마다 **근거 표기**가 붙습니다 — `문서 명시`(라인 번호 포함) / `추론` / `(문서에 명시되지 않음 — 확인 필요)`
- **검증 분석서 마크다운 복사** 버튼 → Notion·티켓에 표·mermaid 그대로 붙여넣기
- **요약 탭에서 파일을 직접 올릴 수 있습니다** — TC 생성 없이 요약·분석서만 생성


**§2 URL 추출이 인식하는 표기**

마크다운 링크(라벨을 화면 이름으로) · 마크다운 표(첫 셀 = 화면, 권한 셀 = 접근 권한) · `URL:` `경로:` 라벨 표기(슬래시 없이 적어도 인식) · `GET /api/posts` 메서드 표기(같은 경로는 한 행으로 합침) · 스킴 없는 사내 도메인(`center.muhayu.com/...`) · 절대 URL.

이미지·소스 파일과 Figma 링크는 제외합니다. 검증 시나리오는 화면 이름에 맞춰 추정합니다 — `목록`은 페이징·정렬, `작성`은 입력 검증, `관리`는 권한 경계, `/api/`는 토큰 직접 호출·파라미터 검증.

**§3 흐름 순서**

`1단계` `Step 1` `①` 같은 단계 표기가 있으면 그 순서대로 직렬 흐름을 그립니다. 표기가 없으면 병렬 배치 후 "화면 전이 순서는 기획 확인 필요"를 캡션에 남깁니다 — 번호 붙은 절 제목은 기능 목록일 뿐이라 순서로 단정하지 않습니다.
**잘못 단정하지 않기 위한 규칙**

- `목적` `범위` `용어` `변경 이력` 같은 메타 섹션은 기능 영역으로 취급하지 않습니다
- 흐름도의 로그인 관문은 영역 이름 자체가 인증을 뜻할 때만 세우고, 인증 요구사항이 개별 기능에 섞여 있으면 관문 없이 구성한 뒤 캡션으로 알립니다

### 4.10 전체 문서 내보내기 (PDF · HTML)

요약 탭의 **전체 문서 PDF 내보내기** 는 문서 요약 + QA 검증 분석서 + 테스트케이스 전문을 하나의 인쇄용 문서로 만들어 인쇄 대화상자를 띄웁니다. 대상을 **"PDF로 저장"** 으로 선택하면 PDF 파일이 만들어집니다. (테스트케이스 탭의 `전체 문서 PDF` 버튼도 동일)

| 항목 | 내용 |
| --- | --- |
| 표지 | 기획서 첫 제목을 프로젝트명으로 · 출처 파일명 · 작성 기준일 |
| 구성 | 문서 요약 → QA 검증 분석서 6개 섹션 → 테스트케이스 전문 |
| 인쇄 품질 | A4 여백, 표 머리행 페이지마다 반복, 행 중간 분리 방지, 주요 섹션 새 페이지 시작 |
| HTML 파일 저장 | 같은 내용을 단일 HTML 로 저장 (첨부·공유용). 열어서 인쇄하면 동일 PDF |

> 서버에서 PDF 를 직접 만들려면 한글 폰트 파일(수 MB)을 임베딩해야 하고, 라이브러리 기본 폰트로는 한글이 깨집니다. 인쇄 경로는 시스템 폰트를 쓰므로 깨짐이 없고 글자가 선택·검색 가능한 상태로 남습니다.

## 5. 사용 방법 (QA 담당자)

1. 기획서 파일을 **끌어다 놓기**
   - 좌측 입력 패널에 놓으면 → 요약 + TC 생성까지 한 번에
   - 우측 **문서 요약** 탭 드롭존에 놓으면 → 요약·검증 분석서만 (TC 생성 없이)
2. 우측 **문서 요약** 탭에서 먼저 확인
   - 수치 기준 표 → 검증에 쓸 입력값 확보
   - 확인 필요 목록 → 기획자에게 질문할 항목 정리
   - **QA 검증 분석서** → 준비 체크리스트대로 환경 세팅, 목표·비목표로 검증 범위 합의
   - `검증 분석서 마크다운 복사` → Notion 검증 문서에 붙여넣기
3. **테스트케이스** 탭에서 검토
   - 유형(Pass/Fail/Edge)·중요도·영역 필터, 시나리오·단계·기대결과·근거 문장 통합 검색
   - 행을 클릭하면 검증 목적·사전 조건·수행 단계·기대 결과·근거 요구사항이 펼쳐짐
   - 불필요한 케이스는 제외하고 누락된 도메인 케이스를 보완
4. **CSV (Excel용·권장)** 으로 내보내 사내 TC 시트에 병합
   - 검증 문서 전체가 필요하면 **전체 문서 PDF 내보내기** (또는 HTML 파일 저장)
5. 기획 변경 시 → **기획서 비교(Diff)** 탭에 이전·신규 문서를 넣고 회귀 대상만 추출

## 7. API 스펙

| 엔드포인트 | 용도 |
| --- | --- |
| `POST /api/extract-text` | 파일 → 기획서 텍스트. raw 바디 + `X-File-Name` 헤더 (멀티파트 파서 불필요) |
| `POST /api/generate-tc` | 기획서 텍스트 → TC 목록 + 문서 요약(`specSummary`) |
| `POST /api/summarize` | 기획서 텍스트 → 문서 요약만 (`useAI: true` 시 서술형 요약 추가) |
| `POST /api/export-csv` | TC 배열(또는 기획서 텍스트) → CSV 다운로드 |
| `POST /api/diff-check` | 이전·신규 기획서 비교 → 변경 요구사항 + 회귀 TC |
| `GET /api/health` | 버전, Node 버전, AI 활성 여부, 업로드 제한 |
| `GET /api/sample` | 샘플 기획서 텍스트 |

> 한글이 포함된 요청 본문은 **UTF-8 파일로 저장해 `--data-binary @request.json`** 으로 보내세요. Windows 터미널에서 인라인 문자열로 보내면 CP949로 전송돼 한글 키워드가 매칭되지 않고 TC가 0건이 됩니다.

## 8. 기술 구성

| 항목 | 내용 |

| 런타임 | Node.js 20+ |
| 서버 | Express 5 — 로컬은 `server.js`, Vercel은 `api/index.js`가 **동일 앱을 재사용** |

| 규모 | 소스 22파일 / 약 3,500줄 |
| 외부 파서 의존 | ZIP·DOCX 파서를 직접 구현해 의존성 최소화 (PDF만 `pdfjs-dist` 사용) |

- PDF 파싱 때문에 함수 메모리 1024MB / 최대 실행 60초로 설정

`ANTHROPIC_API_KEY` 가 설정된 경우에만 동작합니다. 없으면 규칙 엔진만 사용합니다.

- 모델 `claude-opus-5`, adaptive thinking + effort `high`, 스트리밍 수신
- **TC 보강** — 규칙 엔진 결과를 함께 전달해 중복을 피하고, 업무 흐름 전체·상태 조합·데이터 정합성·권한 조합·시간(자정·월말·타임존) 케이스를 추가 생성. 기획서에 없어 확인이 필요한 항목은 제목에 `[기획확인]` 표기
- **요약 보강** — 문서가 무엇을 정의하는지, 핵심 흐름과 깨지기 쉬운 지점, 기획 확인 질문, QA 유의사항을 문장으로 생성

BOM 부착 여부가 줄바꿈 옵션(`excel`)에 묶여 있어, 대시보드의 `CSV` 버튼(`excel: false`)으로 받은 파일에 BOM이 없었습니다. Excel이 CP949로 해석해 한글이 깨졌습니다. `bom` 기본값을 `true`로 고정하고 `excel`은 CRLF/LF만 제어하도록 분리했으며, 회귀 테스트는 문자열 검사 대신 **HTTP 응답 첫 3바이트가 `EF BB BF`인지** 직접 확인합니다.
